# Как в реальной машине

## Одна шина — все слушают

На CAN **нет** роли «только передатчик» или «только приёмник». Каждый ECU:

- подключён к **общей** шине;
- **получает все кадры** (на уровне контроллера);
- **фильтрует** в железе/драйвере по **CAN ID** (маски, списки);
- **передаёт** на свои ID, когда нужно.

Разница между блоками — не в «типе контроллера», а в **логике приложения** и в **настройке фильтров**.

## Что делает наш LinuxCAN

| Реальность | У нас |
|------------|--------|
| ECU + CAN controller | Процесс `linuxcan` + контроллер в `linuxcan-bussim` |
| Шина (доминант/рецессив) | Битовый симулятор шины с wired-AND |
| Арбитраж по ID | Реальный побитный wired-AND |
| CRC-15, bit stuffing, ACK | Считаются и проверяются в `cansim::Bus` |
| TEC/REC, error states | Полноценно: `active` → `passive` → `bus-off` |
| Маска / фильтр RX | `rx.filters[]` — список `{ can_id, encoding, label }` |
| Передача кадра | `tx.can_id` + `publish(payload)` |
| DBC / сигналы | Пока `float32` на `value` (расширяемо) |

Конфиг ECU: `ecus/<name>/ecu.json`

- **engine** — TX `0x100`, слушает `0x200` и `0x300`
- **dashboard** — RX `0x100`, TX `0x300`
- **gateway** — TX `0x200`, слушает `0x100` и `0x300`

## Типовой обмен

1. Engine шлёт значение на **0x100**.
2. Dashboard (фильтр 0x100) принимает и показывает.
3. Dashboard может ответить на **0x300**.
4. Gateway (фильтры 0x100, 0x300) видит оба кадра.

Все видят шину в `candump vcan0` — как в железе. Битовые подробности
(полный кадр, CRC, ACK, шаги арбитража, TEC/REC) — на странице
`http://127.0.0.1:8750/bus.html` и в окне «CAN контроллер» каждого ECU.

Полный разбор битового уровня — [docs/CAN_PROTOCOL.md](CAN_PROTOCOL.md).
